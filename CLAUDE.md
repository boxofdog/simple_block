# Claude Code — Simple Block

## Required safety and scope

- The current direct owner instruction is the only implementation authorization. Never infer authorization from ready status, previous conversation, CI, backlog or documentation. Only explicit owner approval can mark a milestone SHIPPED.
- Read [docs/RULES.md](docs/RULES.md) for lifecycle and document ownership. Every milestone's two-field YAML header is authoritative for status; the [ROADMAP.md](docs/ROADMAP.md) status column is generated.
- Start work by reading the current authorized milestone brief and directly relevant source, rather than every historical milestone, archived report, backlog item or repository summary. Read [REPORTING_POLICY.json](docs/REPORTING_POLICY.json) only when a verification appendix is necessary.
- Do not invent design decisions, commit SHAs, CI runs, artifacts, tests or acceptance. Use NOT RUN or UNAVAILABLE. Preserve conflicts for owner resolution, not silent fixes.
- Only work on the authorized milestone. New worlds only; no old-save migrations, speculative frameworks, unrelated tidy-ups or unapproved changes to shipped rules. Keep rules enforced on the logical server.
- Never overwrite owner-painted textures or editable Blockbench models; painting tasks belong in [Joe's To-Do](docs/Joe's%20To-Do/README.md).
- Make incremental reversible code changes and meaningful game tests/negative controls. Build success alone does not prove real-client tests, remote-client verification or human playtesting.
- Work directly on main per project convention; preserve others' edits.

## Documentation chores automated — stop doing these by hand

The canonical command reference and automation boundaries are in [DOC_AUTOMATION.md](docs/DOC_AUTOMATION.md).

- After explicit owner authorization for a status transition, edit only that milestone's YAML status; the tool mirrors it into ROADMAP. Never manually edit the generated roadmap status cells.
- To collect verified CI run numbers, tested SHA, result and artifacts use: python3 tools/docs/automation.py ci --run-id NUMBER. Alternatively use --latest-successful for the newest successful Build, not an assumed milestone completion. Detailed game-test counts still require independently checked execution evidence.
- Do not hand-maintain README's generated package inventory or docs/evidence/INDEX.md. GitHub Actions regenerates them.
- Structural drift, milestone appendix format, status cells and relative document links are validated automatically. Check with: python3 tools/docs/automation.py drift and python3 tools/docs/check_reporting.py.
- Code-impact hints are advisory and generated by: python3 tools/docs/automation.py impact. Treat matches as suggestions, not permission or proof.
- Only when specifically asked to add a milestone: python3 tools/docs/automation.py new M12 "Title" --write. Default is a harmless preview, new milestones are PLANNED - NOT READY.
- GitHub workflows now limit expensive Build runs to actual build inputs. No standalone milestone reports, repeated status summaries, speculative CI evidence pages, or duplicate decisions ledgers.

## Toolchain and testing

Minecraft 26.3, Fabric Loader 0.19.5, Fabric API 0.162.0+26.3, Loom 1.18.4, Gradle 9.7.1, JDK 25. Minecraft 26.x uses unobfuscated Mojang names: inspect genSources rather than guessing APIs. Mod ID simple_block; package io.github.boxofdog.simpleblock.

- ./gradlew build: production jar and server game tests. ./gradlew runClientGameTest: actual client test. Headless Linux may need xvfb-run and mesa-vulkan-drivers.
- Ore sampling uses runOreSampler in a real world (game-test worlds are superflat); read M02 evidence only for worldgen work.
- The Build workflow publishes simple-block-mod with build-info.json, consumed by the Windows updater. Updates to artifact names/metadata must also update updater tests; see [PLAYTESTING_SETUP](docs/PLAYTESTING_SETUP.md).

## Handoff after authorized implementation

Commit implementation code before documenting verification; execute applicable tests; verify exact CI run, SHA and artifact; append a concise dated implementation/verification note to the same milestone file. Never create another standalone report or claim owner acceptance. Run the documentation checks. Return the changed paths, what was delivered, test results and NOT RUN gaps, reproduction steps, blockers and next owner action. Detailed logs belong under evidence.

M07 remains PLAYTESTING, with an open owner decision on sequential unloading at a side-on Loading Rail. Do not change M06 release behavior or implement M08–M11 without a fresh explicit authorization.
